    GCC & Makefile

    GCC编译程序的四个阶段：

    为了更好的理解GCC的工作过程，我们可以让GCC在预处理、编译、汇编、链接任何一个阶段停止下来，只要加上相关的参数：

    -E 预处理后停下来，生成后缀为.i的预编译文件；

    -S 汇编后停下来，生成后缀为.s的汇编源文件；

    -c 编译后停下来，生成后缀为.o的目标文件。

    现在来理清下整个过程，GCC编译的预处理、编译、汇编、链接四个阶段对应调用的四个工具是cpp、cc1、as、ld，预处理后生成.i的文件，cc1将预处理后的.i文件编译成汇编源文件，as将汇编源文件汇编成.o的目标代码文件，然后通过ld链接成可执行文件。

    1、 预处理（也称预编译）

    进行预编译使用-E参数让gcc在预处理结束后停止编译过程:

    >gcc–E my.c –o my.i

    会发现多了一个my.i的文件，按照gcc首先调用cpp进行预编译，刚好发现MinGW安装目录bin有cpp.exe这个工具，把之前生成的my.i删除，尝试使用cpp –Emy.c –o my.i进行预编译，发现也会生成一个my.i，my.i文件是预编译文件，查看该文件发现stdio.h的内容确实插到文件中去了，其他应当被预处理的宏定义也作了相应的处理。

    2、 编译将源代码文件编译成汇编代码

    gcc –S my.c –o my.s也可以使用gcc –S my.i –o my.s效果是一样的，为了更好理解GCC编译过程，使用gcc –S my.i –o my.s刚好利用了前面第一步预处理生成的my.i文件。按照GCC是调用cc1进行编译的，开始在MinGW安装位置的Bin文件夹并没找着cc1.exe，后来在MinGW安装位置的libexec目录往下找找到了，将my.i文件放到cc1.exe的同级目录下，用cc1 –S my.i –o my.s发现GCC的确是调用cc1进行编译。

    3、 汇编

    第三步，汇编。将第二步生成的my.s源文件汇编成目标代码文件，使用gcc –c my.c –o my.o或gcc –c my.i –o my.o或gcc –c my.s –o my.o或as my.s –o my.o，根据GCC在编译阶段是调用as将汇编源代码进行编译，使用as my.s –o my.o进行编译。

    4、 链接

    第四步，链接。将第三步生成的my.o目标文件链接成可执行文件，使用gcc my.c –o my或gcc my.i –o my或gcc my.o –o my，按照GCC是调用ld来链接的可是使用ld my.o –o my会出现undefined reference to __main'、undefined referencetoprintf'的错误，加上-lc参数又显示找不到-lc，但是在linux下使用ld –e main my.o –lc –o my没问题，我用的是Fedora23的虚拟机，估计在windows下对应的c库没找着，暂时放在这。

    GCC文件类型：

    .c为后缀的文件，C语言源文件

    .a为后缀的文件是由目标文件构成的档案库文件

    .C、.cc、.cpp、.C++、.cp或.cxx为后缀的文件，是C++源文件

    .h为后缀的文件，是程序所包含的头文件

    .i为后缀的文件是已经预处理过的C源代码文件

    .ii为后缀的文件是已经预处理过的C++源代码文件

    .m为后缀的Objective-C源代码文件

    .o为后缀的文件是编译后的目标文件

    .s为后缀的文件是汇编语言源代码文件

    .S为后缀的文件是经过预编译的汇编语言源代码文件

    GCC在各阶段的角色

    Gcc首先调用cpp进行预处理，在预处理过程中队源代码文件中的文件包含（include）、预编译语句（如宏定义define等）进行分析。接着调用cc1进行编译，这个阶段根据输入文件生成以.o为后缀的目标文件。汇编过程就是针对汇编语言的步骤，调用as进行工作，一般来讲，.S为后缀的汇编语言源代码文件和.s为后缀的汇编语言文件经过预编译和汇编后都生成以.o为后缀的目标文件。当所有的目标文件都生成之后，Gcc就调用ld来完成最后的关键性工作，这个阶段就是链接，在链接阶段所有的目标文件被安排在可执行程序的恰当位置，同时，该程序所调用到的库函数也从各自所在的库连到合适的地方。

    可以创建子命令，如make test，编译并运行测试，make release，使用编译优化进行编译并生成tarball，and uploads。

    可以完成整个pipeline，idea is to reduce the effort that you have to do as any part of your build process，就是减少每个过程中需要做的事情

    依赖项会很多，比如shell脚本里调用的函数，会默认目标机器上有这个。所以并不需要声明所有你需要的依赖项。在所有需要依赖项的地方，都会有管理依赖项的工具。大多数时候依赖项都被存储在代码仓库repository里。代码仓库是一个可以安装的代码的集合。creat.io for rust npm for node.js，cryptographic keys，有一种仓库是系统自带的，apt在Ubuntu。仓库有些是官方的，有些是open的。使用open的仓库要注意安全性。

    当你开始使用仓库时，很常见的现象是软件是有版本的，为什么软件有版本，因为没有版本的话，API的改变会导致依赖该API的软件崩溃。

    semantic versioning语义版本号

    major versioning，minor version，patch(补丁) version

    引入了不兼容的东西的情况，一般需要升级大版本号

    3.5能跑的代码，理论上3.6 3.7 3.8也能跑，但是3.5能跑的代码，3.4就不一定能跑，这样就使得在不同的软件之间共享依赖成为可能。

    想要兼容性越好，就需要在大版本号相同的前提下让依赖的版本号尽可能低一点

    if you can depend on major and then minor and patch zero zero that is the best possible dependency you can have. Because it is completely liberal as to which version of that major you're depending on. sometimes this is hard right, sometines you genuinely need a feature that was added but the lower you can get the better it is for those who want to depend on your software in turn

    lock files，用来表明软件依赖的版本。如果没有lockfile，那就需要每次下载最新版本的依赖，然后进行编译，会很费时。有了lockfile就可以手动选择升级的时间，编译过程就会快很多。再有就是获得reproducible builds，不然的话在不同的机器上进行编译或者安装，就有可能因为依赖项不同，导致编译出来的软件也不同。例如依赖项引入了新的bug。但是开发者使用的老版本是OK的。lockfile冻结了ecosystem

    git简单教程

    首先，明白一个道理：已经交由git保存的文件就不能像原来那样随意的进行手动删除了。任何改动，都应该先告知git，由git通过后，再用手动的方式删除。你不是一个人在工作，而是通过git和版本控制系统协同工作。

    理解git的数据模型，然后再理解在每一条命令背后，Git对数据模型做了哪些操作。

    datamodel

    git采用树形数据结构

    每一个snapshot是一棵树，是被追踪的文件夹的最顶层的树，这棵树除了包含两部分信息：

    一部分是这个快照自己的信息：author，commit message，hash code

    另一部分是这个快照包含的修改信息：tree和blob的集合。把folder作为tree，把file作为blob，tree 可以包含tree和blob

    snapshot之间是线性关系，所有的snapshot构成一个directed acyclic graph有向无环图，这就是git的历史记录history，其中每个快照都有其父节点、提交不可被改变、提交中的错误可以用新的提交修正

    type blob=array

    type tree=map

    type commit=struct+something

        parents=array<commit>

    author string

    snapshot  tree

    对于git来说：

    1. 提交/tree/blob都是对象 type object = blob|tree|commit
    2. git不保存对象本身，而是保存其哈希值 object=map
    3. 引用是指向提交的指针，并且可读性好。如master和head

    git仓库只存储对象和引用 reference=map

    这里存储的只是id，并非真正的对象。所有的对象都通过hash追踪

    哈希值是160个字符，

    所有的git命令都只是在操作引用数据和对象数据

    in git, all objects are cotent addressed

    思维导图（本地资料，未发布）

    1. Git包含三个区域：工作目录(Working Directory)、 暂存区域(Staging Area)以及仓库本身。开发者首先在工作目录中对文件进行修改， 修改完成后将修改提交到暂存区域，并最终提交到仓库中。
    2. Git的核心思想之一就是将开发活动分散的尽量小和频繁的提交中(small and frequent)。 暂存区域可以很好的帮助开发者每次只从工作目录中选取一部分修改提交到仓库中。
    3. 使用 git status 查看当前目录状态，可以看到有一个未被跟踪的文件untracked使用 git add untracked 添加该文件(修改)到暂存区域(Staging Area)。

    再次使用 git status 查看当前目录状态，可以看到所有文件已被跟踪。

    1. 如果你对某些文件进行了重命名或删除，你可能需要再次将其添加 到暂存区域(Staging Area)，你也可以使用git mv和git rm 来进行相应的操作，这样Git会自动完成其他工作。
    2. 现在的暂存区已经准备就绪，可以进行你的第一次提交了。Git提交通常需要包含提交消息(Commit Message)以便帮助你和其他合作者理解这次提交的内容。可以使用git commit -m "commit message" 来创建提交并将提交信息与命令放在同一行。运行下面的命令，创建你的第一个提交(提交untracked到仓库)，" "中的内容请自行替换。

    git commit -m "your commit message"

    运行 git log 查看最新的提交记录。

    在 git commit 后添加 -s 选项可以自动在commit message中添加 signed-off-by: xxx 信息。

    1. 一般我们总会有些文件无需纳入 Git 的管理，也不希望它们总出现在未跟踪文件列表。 通常都是些自动生成的文件，比如日志文件，或者编译过程中创建的临时文件等。 在这种情况下，我们可以创建一个名为 .gitignore 的文件，列出要忽略的文件的模式。

    运行下面的命令为你的Git目录创建.gitignore文件：

    echo '*.tmp' > .gitignore

    git add .gitignore

    git commit -m 'add .gitigonre file'

    文件 .gitignore 的格式规范如下：

    • 所有空行或者以 # 开头的行都会被 Git 忽略。
    • 可以使用标准的 glob 模式匹配，它会递归地应用在整个工作区中。
    • 匹配模式可以以 / 开头防止递归。
    • 匹配模式可以以 / 结尾指定目录。
    • 要忽略指定模式以外的文件或目录，可以在模式前加上叹号 ! 取反。
