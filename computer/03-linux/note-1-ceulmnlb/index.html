    Kernel Dev

    内核开发分为不同的时间段

    有一个merge Window，可以添加新的feature。窗口结束之后，发release candidate版本，也就是rc版，大概每周一次，发6-9个rc版之后，发stable release，也就是正式版。窗口结束到stable release之间只能提bugfix，不能提新feature。稳定版发布之后，就会被交给stable team负责，用第三位数字的小版本号发补丁。补丁会被合并到下一次开发的mainline里。

    补丁的生命周期：

    补丁需要被审查，并且补丁必须实现了希望被合并进mainline的改变。

    补丁被合并进mainline的流程：

    Design、早期review、wider review

    设计阶段理论上不需要社区参与，但是尽量早一点公开设计，减少后续重新设计的时间。

    早期review：补丁被post到相关的邮件列表，列表里的开发者回复所有的评论。这个过程会发现绝大多数问题

    wider review：接近主线之后，这个补丁应该被一个相关子系统的维护者接受，但是接受了不代表就一定会进mainland，这个补丁会和相关的子系统一起接受测试，从而发现问题。

    合并到mainline，然后会有更多的comments或者问题可能会在这时出现，这时需要开发展负责任地修复这些问题

    stable release阶段：这一阶段可能会被这个补丁影响的人更多了，所以新的问题可能继续出现

    long-term maintenance长期维护阶段：此时仍需要继续维护，

    内核的不同子系统：networking, specific architecture support, memory management, video devices, etc

    一个子系统有一个指定的维护者。

    每一个上级系统都信任自己的子系统的维护者。

    邮件列表

    将列表发送到单独的文件夹，而不是您的主邮箱。 人们必须能够持续一段时间忽略流。

    不要试图跟踪每一次对话——没有其他人这样做。 过滤感兴趣的主题（但请注意，长时间运行的对话可能会在不更改电子邮件主题行的情况下偏离原始主题）和参与人员非常重要。

    不要喂巨魔。 如果有人试图激起愤怒反应，请忽略他们。

    当回复 linux 内核电子邮件（或其他列表上的电子邮件）时，请为所有相关人员保留 Cc: 标头。 如果没有强有力的理由（例如明确的请求），您绝对不应该删除收件人。 请始终确保您要回复的人位于抄送：列表中。 这种约定也使得没有必要明确要求在对您的帖子的回复中进行复制。

    在提问之前搜索列表档案（以及整个网络）。 一些开发人员可能会对那些明显没有做好功课的人感到不耐烦。

    使用交错（“内联”）回复，这使您的回复更易于阅读。 （即避免置顶 - 将您的答案放在您要回复的引用文本之上的做法。）有关更多详细信息，请参阅 Documentation/process/submitting-patches.rst。

    在正确的邮件列表上询问。 Linux 内核可能是一个通用的集合点，但它并不是寻找所有子系统开发人员的最佳场所。

    最后一点——找到正确的邮件列表——是新手开发人员常犯的错误。 在 linux-kernel 上提出网络相关问题的人几乎肯定会收到礼貌的建议，转而在 netdev 列表上提问，因为这是大多数网络开发人员经常光顾的列表。 SCSI、video4linux、IDE、文件系统等子系统还存在其他列表。 查找邮件列表的最佳位置是与内核源代码一起打包的 MAINTAINERS 文件。

    关于如何开始内核开发过程的问题很常见——

    来自个人和公司。 同样常见的是失误，这使得关系的开始变得更加困难。

    公司通常希望聘请知名开发人员来组建开发团队。 事实上，这可能是一种有效的技术。 但它也往往很昂贵，而且对于扩大有经验的内核开发人员队伍没有多大作用。 只要投入一些时间，就可以让内部开发人员加快 Linux 内核的开发速度。 利用这段时间可以为雇主提供一群既了解内核又了解公司的开发人员，并且他们也可以帮助培训其他人。 从中期来看，这通常是更有利可图的方法。

    可以理解的是，个人开发者常常不知从何开始。 从一个大项目开始可能会令人生畏； 人们常常想先用较小的东西来试水。 正是在这一点上，一些开发人员开始创建补丁来修复拼写错误或较小的编码风格问题。 不幸的是，这样的补丁会产生一定程度的噪音，分散整个开发社区的注意力，因此它们越来越受到轻视。 希望通过这些方式向社区介绍自己的新开发人员将无法获得他们希望的那种接待。

    对于所有内核初学者来说，#1 项目肯定应该是“确保内核始终在您可以接触到的所有机器上完美运行”。 通常做到这一点的方法是与其他人合作来修复问题（这可能需要坚持！）但这很好 - 这是内核开发的一部分。

    在没有明显问题需要修复的情况下，建议开发人员总体上查看当前的回归列表和未解决的错误。 从来不缺少需要解决的问题； 通过解决这些问题，开发人员将获得流程经验，同时赢得开发社区其他成员的尊重。

    对于和设备树绑定的补丁，读提交设备树绑定的补丁文档

    本文档假定你使用git来准备补丁。不熟悉git的需要去学习如何使用，这会让事情变得容易得多。一些子系统对于工作流和expectation有更多的要求，https://www.kernel.org/doc/html/latest/process/maintainer-handbooks.html#maintainer-handbooks-main

    获取当前的源码树

    git clone git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

    这是主线仓库。

    注意，不要直接对主线仓库进行开发，大多数子系统的维护者有他们自己的树，并且希望收到对他们的树的补丁。在主仓库里找到MAINTAINERS文件找到具体的维护者的仓库。如果tree没有被列出的话，直接问维护者也可以。

    描述你的改变

    描述你的问题，无论是一行代码的bugfix还是五千行代码的新特性，肯定有什么原因驱使你这样做，说服reviewer，有一个问题值得被修复，并且阅读它们是有意义的。
