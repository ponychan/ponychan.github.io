    Linux系统提供了几百个system call（软中断触发，切换到内核态）

    glibc对这些system call进行了进一步的封装，对外暴露的接口就是POSIX API标准的（unistd.h就是POSIX API的声明文件）

    Linux 系统调用 (System Call) 全面指南

    一、Linux 系统调用概览

    系统调用是用户空间程序与内核交互的唯一合法接口，**约 400 个**，按功能可分为 10 大类：

    类别 数量 代表系统调用 核心功能
    文件操作 \~70 open/read/write/close 文件读写与控制
    进程管理 \~40 fork/execve/exit/waitpid 进程创建与终止
    内存管理 \~15 brk/mmap/munmap/mprotect 内存分配与保护
    网络通信 \~60 socket/bind/connect/sendto 网络连接与数据传输
    设备控制 \~25 ioctl/poll/select/epoll_ctl 设备 I/O 与多路复用
    信号处理 \~10 kill/sigaction/rt_sigreturn 信号发送与处理
    用户/权限管理 \~20 setuid/getgid/capget/chmod 权限控制与切换
    时间管理 \~10 gettimeofday/clock_gettime/nanosleep 时间获取与休眠
    进程间通信 (IPC) \~30 shmget/msgrcv/semop/pipe 共享内存/消息队列/信号量/管道
    系统控制 \~20 reboot/sysinfo/uname/prctl 系统信息获取与控制

    注：实际数量因内核版本而异（Linux 5.15 约 450 个）

    三、核心系统调用详解（附应用场景）

    1. 文件操作类

    // 打开文件
int fd = open("file.txt", O_RDWR | O_CREAT, 0644);
    • 场景：创建日志文件、读写配置文件

    • 关键参数：

    • O_RDONLY/O_WRONLY/O_RDWR：读写模式

    • O_CREAT：文件不存在时创建
    • O_APPEND：追加写入

    2. 进程管理类

    pid_t pid = fork();
if (pid == 0) {
    // 子进程执行新程序
    execl("/bin/ls", "ls", "-l", NULL);
} else {
    waitpid(pid, &status, 0); // 等待子进程结束
}
    • 场景：Web 服务器处理请求、Shell 执行命令
    • 关键调用链：fork() → execve() → waitpid()

    3. 内存管理类

    // 动态扩展堆内存
void *ptr = sbrk(4096);  // 传统方式
void *ptr = mmap(NULL, 4096, PROT_READ|PROT_WRITE, 
                MAP_PRIVATE|MAP_ANONYMOUS, -1, 0); // 现代方式
    • 场景：malloc() 底层实现、大型文件映射
    • 性能对比：
    操作 brk/sbrk mmap
    小内存分配 ✅ 高效 ❌ 开销大
    大内存块 (>128KB) ❌ 碎片化严重 ✅ 直接映射
    文件映射 ❌ 不支持 ✅ 高效

    4. 网络通信类

    // 创建 TCP 服务器
int sock = socket(AF_INET, SOCK_STREAM, 0);
bind(sock, (struct sockaddr*)&addr, sizeof(addr));
listen(sock, 5);
int client = accept(sock, NULL, NULL);
    • 场景：HTTP 服务器、数据库连接
    • 关键系统调用：socket() → bind() → listen() → accept() → recv()/send()

    5. 多路复用 I/O

    // epoll 高效处理大量连接
int epfd = epoll_create1(0);
struct epoll_event ev;
ev.events = EPOLLIN;
epoll_ctl(epfd, EPOLL_CTL_ADD, sock, &ev);

while (1) {
    int nready = epoll_wait(epfd, events, MAX_EVENTS, -1);
    for (int i = 0; i < nready; i++) {
        if (events[i].data.fd == sock) 
            handle_connection();
    }
}
    • 场景：高并发服务器（Nginx/Redis）
    • 技术演进：select() → poll() → epoll (Linux 2.6+) → io_uring (Linux 5.1+)

    四、系统调用使用规范

    1. 直接调用方式

    #include <sys/syscall.h>

// 获取当前进程 ID
long pid = syscall(SYS_getpid);

// 写文件描述符
const char msg[] = "Hello";
syscall(SYS_write, STDOUT_FILENO, msg, sizeof(msg));

    2. 错误处理模板

    int fd = open("file.txt", O_RDONLY);
if (fd == -1) {
    switch(errno) {
        case ENOENT:
            perror("文件不存在"); // 输出: "文件不存在: No such file or directory"
            break;
        case EACCES:
            perror("权限不足");
            break;
        default:
            perror("open 失败");
    }
    exit(EXIT_FAILURE);
}

### 二、逐层详解

#### 1. **System Call (系统调用)**

- **定位**：\*\*内核暴露的底层接口\*\*（约 300+ 个）  
- **作用**：用户态程序请求内核服务的\*\*唯一合法入口\*\*  
- **特点**：  

  - 通过软中断（`int 0x80`/`syscall`指令）触发  
  - 执行代价高（需切换内核态）  
- **示例**：  

  | **系统调用号** | **功能** | **C 函数名** |
  |-|-|-|
  | 0 | 读文件 | `sys_read` |
  | 1 | 写文件 | `sys_write` |
  | 39 | 创建进程 | `sys_fork` |

#### 2. **POSIX API**

- **定位**：\*\*跨 UNIX 系统的操作规范\*\*（IEEE 标准）  
- **作用**：定义 **进程/文件/线程/信号** 等操作的\*\*函数原型和行为\*\*  
- **关键头文件**：  

  - `<unistd.h>`：文件/进程操作（`fork`, `read`, `write`）  
  - `<pthread.h>`：线程操作  
  - `<sys/socket.h>`：网络通信  
- **特点**：  

  - **抽象接口**（不提供实现）  
  - 符合 POSIX 的代码可在 Linux/macOS/BSD 等系统编译  

#### 3. **glibc (GNU C Library)**

- **定位**：\*\*POSIX 标准在 Linux 上的具体实现\*\*  
- **核心职责**：  

  - 将 POSIX API \*\*映射为系统调用\*\*（如 `open()` → `sys_open`）  
  - 提供 \*\*ANSI C 标准库\*\*（`printf`, `malloc`）  
  - 实现 \*\*扩展功能\*\*（如动态链接 `ld-linux.so`）  
- **文件示例**：  

  ```C
  // glibc 中 open() 的实现伪代码
  int open(const char *path, int flags) {
      return syscall(SYS_open, path, flags); // 调用内核系统调用
  }
  ```

#### 4. **unistd.h**

- **定位**：\*\*POSIX API 的声明头文件\*\*  
- **作用**：提供 **文件访问/进程控制** 等函数原型  
- **关键内容**：  

  ```C
  // 函数声明
  ssize_t read(int fd, void *buf, size_t count);
  pid_t fork(void);

  // 常量定义
  #define STDIN_FILENO  0   // 标准输入文件描述符
  #define STDOUT_FILENO 1   // 标准输出
  ```

#### 5. **Runtime Library (运行时库)**

- **定位**：\*\*程序执行期间必需的支撑库集合\*\*  
- **组成**：  

  | **组件** | **功能** | **是否属于 glibc** |
  |-|-|-|
  | 动态链接器 | 加载共享库 (`ld-linux.so`) | ✅ |
  | 数学库 | `sin()`, `cos()` (`libm.so`) | ✅ |
  | 线程库 | `pthread` 实现 (`libpthread.so`) | ✅ (现代 glibc 已合并) |
  | LLVM/Go 运行时 | 非 C 语言所需（如 `libgcc`） | ❌ |

### 三、交互流程示例：`write()` 执行全路径

```Plain Text
sequenceDiagram
    App->>+glibc: write(fd, buf, len)   // 调用 POSIX API
    glibc->>+内核: syscall(SYS_write, ...) // 封装系统调用
    内核-->>-glibc: 执行结果
    glibc-->>-App: 返回写入字节数

    四、关键对比总结

    概念 层级 是否可执行 是否跨平台 典型代表
    System Call 内核接口 ❌（需封装调用） ❌ (Linux 独占) sys_read, sys_open
    POSIX API 标准规范 ❌（需实现） ✅ (Unix-like) fork(), pthread_create()
    glibc 库实现 ✅ (动态库) ❌ (Linux 专用) libc.so.6, ld-linux.so
    unistd.h 头文件 ❌（声明用） ✅ read(), write() 声明
    Runtime Library 运行时环境 ✅ (多库组合) ⚠️ (部分通用) libc, libm, libgcc

    五、开发者视角：如何选择？

    1. 需要最大兼容性 → 使用 **POSIX API**（如 open() 而非 Windows API）
    2. 需要极致性能 → 谨慎使用**系统调用**（避免频繁内核切换）
    3. 开发 Linux 应用 → 依赖 glibc 实现（注意版本兼容性）
    4. 操作文件描述符 → 包含 **unistd.h**（使用 STDOUT_FILENO 等常量）
    5. 解决运行时依赖 → 链接 **Runtime Library**（如 gcc main.c -lm -lpthread）

    黄金法则：

    • 99% 场景使用 **glibc 实现的 POSIX API**（如 write()）
    • 仅在 内核开发/性能优化 时直接调用系统调用（如 syscall(SYS_write, ...)）
    • 避免绕过 glibc 直接调 syscall：丧失安全性检查（如 FORTIFY_SOURCE）

    系统调用和POSIX API分别在哪个文件里定义

    系统调用（System Calls）和POSIX API在操作系统中的定义位置有本质区别，分别对应内核实现和标准接口规范。以下是具体分析：

    系统调用/usr/src/linuxheader/include/linux/下面的一堆头文件里有一个syscalls.h

    POSIX API在unistd.h里定义

    📁 一、系统调用的定义位置（内核层实现）

    系统调用是操作系统内核提供的底层服务接口，其定义和实现位于 Linux内核源代码 中：

    1. 系统调用表（调度入口）

    2. 文件路径：arch/<架构>/kernel/sys_call_table.c

      • 示例：x86_64架构 → arch/x86/entry/syscalls/syscall_64.tbl
      • 作用：存储系统调用号与内核处理函数的映射关系（如 __NR_read 对应 sys_read 函数）。
      • 示例代码片段：

      C // arch/x86/entry/syscalls/syscall_64.tbl 0 common read sys_read 1 common write sys_write 2 common open sys_open 2. 系统调用实现（内核函数）

    3. 文件路径：kernel/<功能模块>.c

      • 文件操作：fs/read_write.c（实现 sys_read、sys_write）
      • 进程控制：kernel/fork.c（实现 sys_fork）
      • 内存管理：mm/mmap.c（实现 sys_mmap）
      • 特点：每个系统调用以 sys_ 前缀命名（如 sys_open 在 fs/open.c 中定义）。
      • 系统调用号（编号定义）

    4. 文件路径：arch/<架构>/include/uapi/asm/unistd.h

      • 示例：x86_64 → arch/x86/include/uapi/asm/unistd_64.h
      • 内容：为每个系统调用分配唯一编号（如 #define __NR_open 5）。

    📄 二、POSIX API的定义位置（标准接口层）

    POSIX API 是 **跨平台标准规范**，其函数原型在头文件中声明，具体实现由C库（如glibc）完成：

    1. 核心头文件

    2. unistd.h：声明进程控制、文件I/O等基础API（如 fork(), read(), write()）。

    3. 其他关键头文件：

      • <pthread.h>：线程管理（pthread_create）
      • <sys/socket.h>：网络通信（socket）
      • <fcntl.h>：文件控制（open 的标志位常量）。
      • 标准文档定义

    4. POSIX规范文本（如 IEEE Std 1003.1-2017）详细描述API行为，不涉及具体代码。

    5. 示例：fork() 的行为在标准中定义为“创建新进程”，具体实现由操作系统提供。

    6. C库实现（如glibc）

    7. glibc 源码中封装系统调用：

      • read() 的封装在 sysdeps/unix/sysv/linux/read.c
      • fork() 的封装在 sysdeps/nptl/fork.c。

    🔍 三、关键区别对比

    特性 系统调用 POSIX API
    定义位置 内核源码（.c 和 .tbl 文件） 标准头文件（如 unistd.h）
    实现者 操作系统内核 C库（如 glibc）
    调用方式 通过软中断（syscall指令） 普通函数调用
    可移植性 操作系统相关（Linux特有） 跨Unix系统（遵循POSIX）
    示例 sys_read（内核函数） read()（声明在 unistd.h）

    💻 四、查询与验证方法

    1. 查看系统调用

    2. 命令：grep -r "SYSCALL_DEFINE" /usr/src/linux-kernel/（搜索内核源码）

    3. 工具：strace -e trace=open,read ./program（跟踪程序调用的系统调用）。

    4. 查看POSIX API声明

    5. 命令：man 2 read（查看read系统调用的手册）

    6. 代码：包含 <unistd.h> 后通过预处理器输出宏定义：gcc -E -dD program.c。

    💎 总结

    • 系统调用：在内核源码中实现（如 sys_read 在 fs/read_write.c），通过系统调用表调度。
    • POSIX API：在标准头文件声明（如 unistd.h），由C库封装系统调用提供跨平台兼容性。

    开发者应优先使用POSIX API保证可移植性，仅在深度优化时直接调用系统调用。

    glibc动态与静态，可执行与共享库的区别

    glibc 的静态链接与动态链接在可执行文件和共享库中的应用存在本质差异，直接影响程序的部署、兼容性和性能。以下是深度解析：

    一、核心概念对比

    1. 静态链接 vs 动态链接

    特性 静态链接 动态链接
    链接时机 编译时完成 运行时完成
    glibc 整合 库代码**直接嵌入**可执行文件 仅记录依赖，运行时加载 /lib/libc.so.6
    文件大小 显著增大（含完整库代码） 极小（仅自身代码）
    内存占用 每个进程独立占用 多个进程**共享**同一物理内存中的 glibc
    更新依赖 需重新编译程序 替换 .so 文件即生效
    典型场景 嵌入式系统、无依赖部署 桌面/服务器应用、容器化环境

    2. 可执行文件 vs 共享库

    类型 可执行文件 (ELF Executable) 共享库 (ELF Shared Object)
    入口点 _start 符号（由 crt0.o 定义） 无固定入口，提供函数符号表
    加载方式 由内核直接加载 execve() 由动态链接器 ld-linux.so 加载
    链接标志 gcc -o prog prog.c gcc -shared -fPIC -o libfoo.so foo.c
    内部结构 含 .text、.data、程序头表 含 .plt、.got 等重定位表
    依赖关系 可静态/动态依赖库 只能动态链接其他库

    二、glibc 在四种组合中的行为差异

    1. 静态链接的可执行文件

    gcc -static -o prog_static prog.c  # 强制静态链接
    • 文件结构：

    ```Bash $ file prog_static prog_static: ELF 64-bit LSB executable, statically linked...

    $ ldd prog_static not a dynamic executable # 无动态依赖 ``` - glibc 位置：

    • 完整 glibc 代码（libc.a）被提取并合并到可执行文件的 .text 段
    • 内存映射：!每个进程独立加载完整的 glibc 副本

    2. 动态链接的可执行文件

    gcc -o prog_dynamic prog.c  # 默认动态链接
    • 文件结构：

    Bash $ readelf -d prog_dynamic | grep NEEDED 0x0000000000000001 (NEEDED) Shared library: [libc.so.6] - 运行时加载：

    Plain Text sequenceDiagram 程序->>ld-linux.so: execve() 触发加载 ld-linux.so->>libc.so.6: 按需加载 glibc libc.so.6-->>程序: 提供函数实现 - 内存优化：10 个进程运行相同程序 → **1 份 glibc 物理内存**（通过 COW 机制共享）

    3. 静态链接的共享库（罕见且危险）

    gcc -static -shared -o libbad.so foo.c  # 错误用法！

    • 问题分析：

    • 违反共享库设计原则（本应被共享）

    • 导致符号冲突（多个库嵌入相同 glibc 代码）
    • 实际场景中几乎从不使用

    4. 动态链接的共享库（标准做法）

    gcc -shared -fPIC -o libfoo.so foo.c  # 正确编译

    • 关键要求：

    • -fPIC：生成位置无关代码（可在任意地址加载）

    • 无 main 函数：仅暴露函数符号（如 libcurl.so 的 curl_easy_init()）
    • 依赖关系：

    Bash $ objdump -p libfoo.so | grep NEEDED NEEDED libc.so.6 # 依赖 glibc

    三、技术细节深度解析

    1. 静态链接的代价

    // 示例：静态链接的可执行文件符号表
$ nm prog_static | grep " T "
0000000000401000 T _start
0000000000401030 T main
0000000000402580 T malloc  # glibc 的 malloc 被复制进来

    • 空间放大效应：一个简单的 printf("Hello") 程序：

    • 动态链接：8 KB

    • 静态链接：**2 MB**（增加 250 倍）

    2. 动态链接的重定位机制

    // 动态链接的可执行文件结构
$ objdump -d prog_dynamic
...
<printf@plt>:
  4003a0: ff 25 72 0c 20 00    jmpq *0x200c72(%rip)  # 跳转到 GOT 表
  4003a6: 68 00 00 00 00       pushq $0x0
  4003ab: e9 e0 ff ff ff       jmpq 400390 <_init+0x20>
    • 延迟绑定 (Lazy Binding)：首次调用 printf 时，由 ld-linux.so 解析真实地址并写入 GOT 表，后续调用直接跳转。

    3. 兼容性风险矩阵

    链接方式 glibc 升级影响 解决方案
    动态链接程序 依赖目标系统 glibc 版本 容器化或指定最低版本要求
    静态链接程序 锁定编译时的 glibc 行为 安全更新需重新编译
    动态链接库 遵循符号版本控制 (Symbol Versioning) 使用 GLIBC_2.17 等标签

    四、最佳实践指南

    1. 何时选择静态链接？

    • ✅ 嵌入式设备（无稳定 glibc 环境）
    • ✅ 分发闭源二进制（避免依赖冲突）
    • ✅ 安全敏感场景（避免恶意 LD_PRELOAD 注入）
    • ❌ 避免在共享库中使用

    2. 何时选择动态链接？

    • ✅ 桌面/服务器应用（节约内存和磁盘）
    • ✅ 依赖其他共享库（如 GTK 应用链）
    • ✅ 需要热更新 glibc 安全补丁

    3. 混合使用示例

    # 主程序动态链接，内部插件静态链接
gcc -o main main.c -ldl           # 主程序动态链接
gcc -static -o plugin.so plugin.c # 错误！共享库不能静态编译

# 正确做法：插件也动态链接
gcc -shared -fPIC -o plugin.so plugin.c

    关键原则：共享库必须动态链接以保持兼容性

    五、诊断工具速查

    任务 静态链接工具 动态链接工具
    查看依赖库 strings prog \| grep GLIBC ldd prog
    分析符号定义 nm prog_static nm -D prog_dynamic
    跟踪运行时加载 N/A LD_DEBUG=libs ./prog
    检查 PIC 合规性 N/A readelf -d lib.so \| grep FLAGS (FLAGS 含 PIC)

# 驱动开发

在 Linux 驱动开发中，\*\*既不直接使用 glibc，也不直接调用用户态的系统调用\*\*。驱动开发的核心是\*\*内核空间编程\*\*，遵循完全不同的规则和接口体系。以下是关键分析：



---



### 一、Linux 驱动开发的本质

```Plain Text
graph LR
    A[硬件设备] -->|中断/DMA/寄存器| B(内核空间)
    B -->|提供接口| C[用户空间]
    C -->|系统调用| D[应用程序]
    • 驱动位置：内核空间（Ring 0）

    • 核心任务：

    • 管理硬件资源（寄存器、中断、DMA）

    • 实现内核标准接口（如 file_operations）
    • 向用户空间暴露设备节点（如 /dev/input0）

    二、驱动开发的技术栈

    1. 禁用 glibc

    • 原因：

    • glibc 是**用户态库**，依赖内核系统调用

    • 内核驱动**直接访问硬件**，无需通过系统调用层
    • 替代方案：使用**内核内置函数**（头文件在 /lib/modules/$(uname -r)/build/include/linux）

    2. 禁用系统调用（System Call）

    • 原因：

    • 系统调用是**用户程序请求内核服务的接口**

    • 驱动本身**属于内核**，直接调用内部函数
    • 替代方案：实现内核回调接口（如 .read = mydrv_read）

    三、驱动开发核心工具

    1. 内核 API 与头文件

    功能 内核头文件 关键 API 示例
    内存管理 <linux/slab.h> kmalloc(), kfree()
    设备注册 <linux/fs.h> register_chrdev(), cdev_init()
    中断处理 <linux/interrupt.h> request_irq(), free_irq()
    同步机制 <linux/spinlock.h> spin_lock(), mutex_lock()
    延时控制 <linux/delay.h> mdelay(), usleep_range()
    打印调试 <linux/printk.h> printk(KERN_INFO "message")

    注：所有 API 前缀为 __ 的函数（如 __get_free_pages()）禁止在驱动中使用

    2. 设备模型接口

    // 字符设备驱动示例
static const struct file_operations mydrv_fops = {
    .owner = THIS_MODULE,
    .read = mydrv_read,    // 实现读操作
    .write = mydrv_write,  // 实现写操作
    .open = mydrv_open,    // 实现打开操作
};

static int __init mydrv_init(void) {
    register_chrdev(0, "mydrv", &mydrv_fops); // 注册驱动
    return 0;
}

    四、与用户空间的交互方式

    虽然驱动本身不用 glibc/system call，但需**为用户程序提供访问接口**：

    1. 标准设备文件接口

    // 用户程序通过 glibc 调用 read()
ssize_t mydrv_read(struct file *filp, char __user *buf, size_t count, loff_t *fpos) {
    copy_to_user(buf, kernel_buffer, count); // 内核到用户空间复制
    return count;
}

    2. IOCTL 自定义命令

    // 用户程序调用 ioctl(fd, MY_CMD, arg)
long mydrv_ioctl(struct file *filp, unsigned int cmd, unsigned long arg) {
    switch(cmd) {
        case MY_CMD1: ... // 处理自定义命令
        case MY_CMD2: ...
    }
}

    3. sysfs 属性文件

    // 在 /sys/class/mydrv/ 创建可读写属性
static ssize_t value_show(struct device *dev, struct device_attribute *attr, char *buf) {
    return sprintf(buf, "%d\n", reg_value);
}
DEVICE_ATTR_RW(value); // 定义读写属性

    五、驱动开发与用户空间编程的对比

    维度 驱动开发 用户程序开发
    执行空间 内核空间 (Ring 0) 用户空间 (Ring 3)
    内存访问 直接物理地址/虚拟地址 通过系统调用间接访问
    库依赖 内核 API（无 glibc） 依赖 glibc
    错误处理 导致内核 panic/oops 进程终止
    调试工具 printk, ftrace, KGDB gdb, strace, valgrind
    编译方式 内核模块（.ko） 可执行文件/共享库

    六、典型驱动开发流程

    1. 实现核心回调：

    C static struct file_operations fops = { .read = drv_read, .write = drv_write, .open = drv_open, .release = drv_release }; 2. 注册设备：

    C alloc_chrdev_region(&dev, 0, 1, "mydrv"); cdev_init(&cdev, &fops); cdev_add(&cdev, dev, 1); 3. 处理中断：

    C request_irq(irq_num, irq_handler, IRQF_SHARED, "mydrv", dev); 4. 内存管理：

    C buf = kmalloc(BUF_SIZE, GFP_KERNEL); // 动态分配 dma_addr = dma_map_single(dev, buf, size, DMA_TO_DEVICE); // DMA映射 5. 用户交互：

    C copy_from_user(kbuf, user_buf, len); // 从用户空间复制数据

    七、总结：驱动开发的技术定位

    • 内核层：直接操作硬件，使用内核 API（**非 glibc/system call**）
    • 接口层：通过 file_operations 等结构体向用户空间暴露能力
    • 用户层：应用程序通过 glibc → 系统调用 → 驱动回调 访问硬件

    关键原则：

    • 驱动开发 = 内核模块编程，禁用任何用户空间库
    • 用户程序通过 系统调用 访问驱动（如 open("/dev/mydrv")）
    • glibc 在用户空间封装系统调用，与驱动无直接交互
